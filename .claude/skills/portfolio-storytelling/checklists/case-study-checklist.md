# Case Study Checklist

Use for auditing or building a single project case study. Matches the anatomy in [../docs/project-case-study-structure.md](../docs/project-case-study-structure.md).

## Structure

- [ ] Opens with a hook/overview (1–2 sentences) that survives being read alone by a skimmer
- [ ] Does not open with the tech stack
- [ ] States the brief/problem in the client's or project's own terms before any technical framing
- [ ] Real constraints are named (timeline, budget, brand system, target device/audience limits) — not just the deliverable
- [ ] Process is told through specific decisions (option chosen vs. option(s) rejected, and why), not a day-by-day diary
- [ ] At least one technical/creative challenge is described with a named mechanism (what was actually the bottleneck/problem), not a vague "this was complex"
- [ ] The solution to that challenge is concrete enough that a technical reader could evaluate it, not just take it on faith
- [ ] Outcome section separates measurable facts (shipped, live, award, measured metric) from unverifiable claims ("client loved it" without evidence)
- [ ] No fabricated or unverifiable numbers — honest qualitative claims used where a real number isn't available

## Show vs. tell

- [ ] Every major claim has a specific, checkable fact attached (number, named mechanism, before/after) — see the show/tell table in [../docs/project-case-study-structure.md](../docs/project-case-study-structure.md)
- [ ] No unverifiable superlatives ("the most innovative approach")
- [ ] Tool/tech names are attached to the decision they served, not listed as a standalone credibility flex

## Length & pacing

- [ ] Depth matches the project's role in the overall flow — full six-part structure only for thesis-defining projects; lighter treatment elsewhere (see pacing guidance in [../docs/narrative-structure.md](../docs/narrative-structure.md))
- [ ] No exhaustive iteration diary — the single most instructive pivot is told, not every prototype
- [ ] Optional reflection ("what I'd do differently") included if it's genuinely honest — a real seniority signal when present, not required

## Voice

- [ ] Passes a spot-check against [copywriting-checklist.md](copywriting-checklist.md) (active voice, no banned words, specificity)
- [ ] Reads as this specific project — sentences would sound false pasted onto a different case study

## Verification

- [ ] Live link or repo link present, or an explicit honest note if the project is no longer live
- [ ] Any claimed metric could be defended if a technical reader asked "how did you measure that?"
